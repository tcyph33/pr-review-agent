# PR Review Agent

A TypeScript script that runs twice daily to find GitHub PRs requesting your review, runs each one through your `code-review` skill via Claude Code with full local repo access, tracks PR status (open, merged, closed), and saves structured feedback locally. A self-hosted HTML dashboard lets you read feedback, see review state, and open PRs or interactive Claude Code sessions from each card.

---

## How It Works

1. **launchd** triggers `run-reviews.ts` at 2am and 2pm via `tsx`
2. The script refreshes the status of all existing reviews (open, merged, closed)
3. It fetches your `code-review` skill live from your `claude-toolkit` repo
4. It resolves your GitHub username automatically from your token
5. For each PR, Claude Code runs headlessly via `claude --print`, invoking `/code-review <PR_URL>` with the skill as the system prompt — cloning the repo, reading full files, and grepping for issues
6. Results are saved to `results/reviews.json`
7. A macOS notification fires with a new/updated count (skipped on other platforms)
8. `server.ts` serves the dashboard at `http://localhost:3000/dashboard/`

## Setup

### 1. Clone and run setup

```bash
git clone https://github.com/tcyph33/pr-review-agent.git
cd pr-review-agent
bash setup-macos.sh
```

`setup-macos.sh` handles everything automatically:
- Installs npm dependencies
- Creates `logs/` and `results/` directories
- Copies `.env.example` to `.env` (if it doesn't already exist)
- Writes `~/.claude/settings.json` with pre-approved tools for autonomous review (safely merges if the file already exists)
- Generates both launchd plists with the correct absolute paths for this machine
- Loads both launchd jobs

### 2. Configure your keys

The script reads credentials from `process.env`. You have two options — pick either or both:

**Option A — `.env` file** (created by setup-macos.sh):
```
GITHUB_API_TOKEN=ghp_yourTokenHere
REVIEW_SKILL_URL=https://api.github.com/repos/tcyph33/claude-toolkit/contents/skills/code-review/SKILL.md
```

**Option B — environment variables** set in your shell profile or system:
```bash
export GITHUB_API_TOKEN=ghp_yourTokenHere
export REVIEW_SKILL_URL=https://api.github.com/repos/tcyph33/claude-toolkit/contents/skills/code-review/SKILL.md
```

If a variable is set in the environment it takes precedence over `.env`.

| Variable | Description |
|---|---|
| `GITHUB_API_TOKEN` | Personal access token. Needs `pull_requests: read` and `contents: read`. Settings → Developer settings → Fine-grained tokens. |
| `REVIEW_SKILL_URL` | GitHub API URL to your `code-review` skill `.md` file |
| `REVIEW_REQUESTED_REPOS` | Comma-separated list of `owner/repo` to watch for review-requested |
| `REVIEW_ASSIGNEE_REPOS` | Comma-separated list of `owner/repo` to watch for assignee. A repo can appear in both lists. |

### 3. Authenticate GitHub CLI

```bash
gh auth login
```

### 4. Test manually

```bash
npm run review
```

## Dashboard

Open **http://localhost:3000/dashboard/** in any browser.

- Shows all reviewed PRs with agent feedback
- Summary bar: total PRs pending, repos, oldest PR age, average PR age
- Review state badge per card: Pending, Commented, Changes Requested, Approved
- PR status badge per card: Merged or Closed (open PRs shown first, merged/closed dimmed below)
- **Expand/Collapse** each feedback block
- **Open PR** opens that single PR in a new tab
- **Open All** opens every PR at once
- **⬡ Claude Code** opens an interactive Claude Code session in Terminal with full repo context and prior agent feedback loaded
- **Re-run agent** re-reviews that one PR in the background, with **Cancel run** while it goes — see [Re-running one PR](#re-running-one-pr)
- **Dismiss** removes a single review from the dashboard
- **Clear All** wipes all reviews after confirmation
- Auto-refreshes every 60 seconds

### What the status chip means

One chip per card answering "what now", most urgent first. The chip replaces the
raw GitHub fields, which are demoted to the facts line beneath it.

| Chip | Means |
|---|---|
| **Agent running** | A re-run is in progress, with elapsed time |
| **Review failed** | The agent errored on this PR — see the log |
| **Agent re-run needed** | The head moved, so the stored findings describe older code |
| **Needs your review** | Your turn: you have never given feedback, or the author has pushed since you did |
| **Waiting on author** | You have reviewed and nothing has happened since |
| **Approved** | Your approval stands |
| **Merged** / **Closed** | Nothing left to act on |

Two parts of this are deliberate and easy to get wrong when changing it:

**An approval follows GitHub's own rules.** GitHub keeps an approval when new
commits land, unless the repo enables *"Dismiss stale pull request approvals when
new commits are pushed"*. While the approval stands the PR is mergeable and
nothing is needed from you, so the chip says **Approved**. On a repo that does
dismiss, GitHub moves the review to `DISMISSED` and the chip becomes **Needs your
review** — without that, such a PR would read as "Waiting on author" forever
while GitHub was actually waiting on you to re-approve.

**Whose turn it is comes from `lastAuthorPushAt`, not the commit list.**
Dismissing new commits with **No re-run needed** says the agent need not look
again; it must not also decide whose turn it is. Those are separate judgments,
and the commit list is cleared by the first one. So the turn is read from the
newest non-merge commit date compared against your last submitted review — which
also means a merge from the base branch never lands on your plate, since merges
are excluded upstream.

The dashboard server (`server.ts`) starts automatically at login via launchd and restarts itself if it ever crashes.

## Review Skill

The agent uses the `code-review` skill from your `claude-toolkit` repo. The skill:

- Clones the PR branch shallowly to `~/PR-Reviews/<org>-<repo>-<number>` using `gh`
- Reads full file contents — not just the diff — to catch issues in untouched dependent files
- Greps the entire repo for dangling references to removed or renamed concepts
- Runs a structured 9-category checklist (correctness, design, readability, completeness, semantic validity, testing, security, performance, documentation)
- Produces a structured report with a verdict: APPROVE, APPROVE WITH NITS, NEEDS CHANGES, or NEEDS DISCUSSION
- Does **not** post comments to GitHub — the review stays local

### Claude Code Permissions

The agent passes `--allowedTools` on each `claude --print` invocation, granting exactly the tools the skill needs so reviews run without approval prompts:

| Permission | Why |
|---|---|
| `Read` | Reading files from the cloned repo |
| `Bash(gh pr view*)` | Fetching PR metadata |
| `Bash(gh pr diff*)` | Fetching the PR diff |
| `Bash(gh repo clone*)` | Cloning the PR branch |
| `Bash(mkdir*)` | Creating `~/PR-Reviews/` if it doesn't exist |
| `Bash(grep*)` | Searching the full repo for dangling references |

These are scoped to the agent's own runs. **Nothing is written to `~/.claude/settings.json`**, so your interactive Claude Code sessions keep whatever permission rules you set for yourself — a scheduled job should not widen them.

Because a headless `--print` run cannot prompt, a review needing a tool outside this list will fail rather than pause. The list lives in `runWithClaudeCode` in [run-reviews.ts](run-reviews.ts), next to the code that uses it.

> Earlier versions of `setup-macos.sh` merged these permissions into `~/.claude/settings.json`. If you ran it before this change, those entries are still there — harmless, but you can remove them by hand if you'd rather not have them granted globally.

### Open in Claude Code

Each dashboard card has an **⬡ Claude Code** button. Clicking it:

1. Fetches your review skill fresh from `REVIEW_SKILL_URL`
2. Opens a new Terminal window with Claude Code running interactively
3. Passes `/code-review <PR_URL>` as the first message along with the prior agent feedback as context
4. Claude Code runs the full skill against the local repo with the prior feedback already in view

This gives you an interactive follow-up session with the same context the agent had — full repo access, your skill, and the prior review.

### Re-running one PR

**Re-run agent** on a card re-reviews that PR alone, skipping the search and the
no-new-commits check that a scheduled run applies. It is the same work as
`npm run review -- <pr-url>`.

The run happens in the background on the dashboard server, not in a Terminal
window, so nothing has to stay open and the dashboard is usable while it goes:

1. The card's chip switches to **Agent running** with the elapsed time, so an
   in-flight run is visible at a glance from the list
2. **Cancel run** stops the agent. The run is given its own process group, so
   this reaches the agent itself rather than only the wrapping `npm`
3. If it fails, a small red **Re-run failed** appears under the card's facts,
   with an ✕ to dismiss it. It is a note rather than a status, because a failed
   attempt does not change what the review itself needs — the chip keeps saying
   that, and the note says the re-run did not happen. Why it failed is in the
   PR's log, which **View Log** in the same footer opens. Cancelling is not a
   failure and shows no note
4. When it finishes, the dashboard picks up the new review within a few seconds
   and the usual notification fires

#### One log per PR

There is a single log per PR, `logs/reviews/<owner>-<repo>-<number>.log`, and
**View Log** shows it. On a re-run the review script owns that file from its
first line, so one file holds the whole run in order: pre-flight, auth, the
skill fetch, the trigger tier, the agent's output, and the outcome. The first
write of a run truncates it; everything after appends.

That matters because the things most likely to break a re-run — expired `gh`
auth, a failed skill fetch, a cap firing — all happen *before* the agent is
reached. They are in the log because the script puts them there, not because
anything tails the process.

The agent's own stderr is logged too, including when it exits cleanly: a
rate-limited or retried API call is often the only explanation for a thin
review, and that warning used to be discarded on success.

A scheduled run deliberately does **not** copy its shared startup output into
every PR's log — it reviews many PRs, and the same preamble repeated fifteen
times would bury the review each log is there for. The orchestration log keeps
that instead.

Two cases cannot reach a PR's log: a malformed PR url, which belongs to no PR,
and a crash before the script's first write. Both are near-impossible in
practice — the dashboard builds the url it re-runs, and the server itself runs
under the same `npx tsx` the run does — so the red note is all they produce. Its
exit code is recorded; there is nothing in the log to read.

#### How a run is kept from going on unnoticed

Three bounds, only the first of which holds when nothing is watching:

- **The run caps itself**, from inside the process, so this holds whatever
  happens to the server. Each cap signals every agent in flight before exiting,
  so `claude` is stopped rather than orphaned, and each covers the wedges the
  per-agent timeout does not — a GitHub request with no timeout of its own, the
  clone, a retry loop
- **The agent has its own timeout.** 30 minutes per `claude` invocation, below
  every run cap so it normally fires first and reports the more specific error
- **The server reaps on exit.** `SIGTERM` and `SIGINT` stop every tracked run
  before the server exits, so a launchd restart or a ctrl-c leaves nothing behind

The caps are per phase, since one generous enough for reviewing would be useless
as a bound on the API calls that come first. Each is derived from what its phase
actually does:

| Phase | Cap | Why |
|---|---|---|
| Starting up — pre-flight, skill fetch, auth, status refresh, PR search | 15 min | All API calls that should take seconds |
| Reviewing (scheduled run) | 45 min | PRs are reviewed in parallel, so this is bounded by the slowest single agent however many there are — 30 for the agent plus slack |
| A single-PR re-run | 40 min | One agent invocation plus a handful of API calls |

> **Known gap:** the list of in-flight runs lives in the server's memory, and a
> `SIGKILL` runs no handler. If the server is killed outright mid-run, the
> dashboard stops showing that run and **Cancel run** is no longer offered for
> it; the run's own cap is what ends it.

Unlike the scheduled run and **⬡ Claude Code**, this path has no macOS
dependency.

## Scheduling (macOS only)

The review script runs at 2:00 AM and 2:00 PM daily via launchd (configured by `setup-macos.sh`). On macOS, a notification fires after each run showing how many reviews are new and how many were updated. On other platforms the notification is skipped silently.

> **Note:** launchd skips runs while the laptop is asleep and does not catch up on missed runs.
> If your laptop is usually closed at 2am, change the hour in the plist to a time it's reliably awake,
> or enable **System Settings → Energy → Wake for network access**.

### Useful commands

```bash
# Trigger the review script right now
launchctl start com.pr-review-agent

# View live logs
tail -f logs/out.log
tail -f logs/err.log

# Reload a job after editing its plist
launchctl unload ~/Library/LaunchAgents/com.pr-review-agent.plist
launchctl load ~/Library/LaunchAgents/com.pr-review-agent.plist

# Check both jobs are registered
launchctl list | grep pr-review
```

## Platform Notes

**Scheduling, the dashboard server, and the "Open in Claude Code" button are macOS only.** The `setup-macos.sh` script, launchd plists, and `launchctl` commands are all macOS-specific. "Open in Claude Code" needs a Terminal window because the session is interactive; **Re-run agent** does not, and works anywhere the server runs.

The `run-reviews.ts` script itself is fully cross-platform. If you want to run this on another OS, only the scheduling layer needs to change:
- **Linux** — use `cron`
- **Windows** — use Task Scheduler

### Running with the Laptop Lid Closed

By default, macOS puts the machine to sleep when the lid is closed, which causes launchd to skip scheduled runs. To allow the script to run with the lid closed:

1. Open **System Settings → Energy**
2. Enable **"Wake for network access"**

To change the schedule after setup:
```bash
open ~/Library/LaunchAgents/com.pr-review-agent.plist

launchctl unload ~/Library/LaunchAgents/com.pr-review-agent.plist
launchctl load ~/Library/LaunchAgents/com.pr-review-agent.plist
```

## Troubleshooting

### A PR review failed overnight

The script catches Claude Code errors per PR and continues — one failure won't stop other reviews. Failed PRs appear on the dashboard as red-bordered cards with a "⚠ Review Failed" badge and a **View Log** button. Click View Log to see the full Claude Code output for that PR directly in the dashboard.

Each run creates a timestamped log at `logs/orchestration/YYYY-MM-DD_HH-MM-SS.log` — the path is printed at the start of every run. Orchestration logs older than 7 days are cleaned up automatically.

Per-PR logs live at `logs/reviews/<owner>-<repo>-<number>.log` and are automatically deleted when you dismiss the card from the dashboard.

Re-run manually to retry a failed review:

```bash
npm run review
```

### Claude Code is hanging

Each PR review has a 30 minute timeout. If Claude Code is waiting for a permission approval that was never pre-approved, it will sit there until the timeout fires, then log a failure and move on.

To find and watch the latest orchestration log:

```bash
ls -t logs/orchestration/ | head -1 | xargs -I{} tail -f logs/orchestration/{}
```

To kill a hung run manually:

```bash
# Find the script process
ps aux | grep "run-reviews"
kill <PID>

# Kill any orphaned claude processes too
pkill -f "claude --print"
```

launchd will not restart the review script after a kill — only the dashboard server auto-restarts. The next scheduled run will start fresh.

### Claude Code prompts for approval on a tool

If the skill tries to use a tool that isn't in `~/.claude/settings.json`, Claude Code will pause waiting for approval. This causes a hang until the 30 minute timeout fires.

To fix it permanently, add the missing tool to `~/.claude/settings.json`:

```json
{
  "allowedTools": [
    "read",
    "bash(gh pr view*)",
    "bash(gh pr diff*)",
    "bash(gh repo clone*)",
    "bash(mkdir*)",
    "bash(grep*)",
    "bash(your-new-tool*)"
  ]
}
```

Then reload the launchd job:

```bash
launchctl unload ~/Library/LaunchAgents/com.pr-review-agent.plist
launchctl load ~/Library/LaunchAgents/com.pr-review-agent.plist
```

The easiest way to discover what tools the skill needs is to run it once manually in an interactive Claude Code session and note any approval prompts that appear.

### GitHub CLI auth expired

The script checks `gh auth status` before running any reviews. If auth has expired you'll get a macOS notification saying "Pre-flight Failed" with the reason, and a clear error in the orchestration log. Re-authenticate with:

```bash
gh auth login
```

No other changes needed — the next run will work automatically.

### claude or gh CLI not found

The script checks for both CLIs at startup. If either is missing you'll get a "Pre-flight Failed" notification and a clear error in the orchestration log.

Install Claude Code:
```bash
npm install -g @anthropic-ai/claude-code
```

Install GitHub CLI:
```bash
brew install gh && gh auth login
```

### PATH issues with launchd

launchd runs with a minimal system PATH that may not include tools installed by Homebrew, nvm, or npm. `setup-macos.sh` resolves the full paths of `npx`, `claude`, `gh`, and `node` at setup time and injects them into the plist via `EnvironmentVariables`. If you install or move a tool after running setup, re-run `setup-macos.sh` to update the paths.

### Verifying autonomous operation

The safest way to confirm everything will run unattended overnight is one clean manual run:

```bash
npm run review
```

If it completes from start to finish with no prompts and no errors in the logs, every future scheduled run will behave identically. This is a one-time check per machine — you never need to repeat it.
